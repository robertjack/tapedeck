`rebuild [--yes]` empties the wiki's content and files the whole library into it again. It
is `sync` from zero: the same eligibility rule, the same order, the same per-video
operation, preceded by a deliberate reset. It exists because SPEC-core-002's argument does
not stop being true at the wiki's edge. Every other layer of tapedeck can be regenerated by
a better tool — a stronger model re-derives the transcripts, `reindex` rebuilds the
database — and the wiki is the one layer SPEC-core-002 does not govern, not because
regenerating it is worthless but because nothing in the library can reconstruct the
particular wiki that exists. A user who rewrites the brief, or swaps the maintainer for a
better one, has changed the thing that produces every page in the wiki, and the pages
already there were written by the old one. `rebuild` is how they get the layer they would
have had, and git is what makes asking for it survivable: the wiki they replace is still in
the history, one `git show` away, restorable long after they decide the new one was a
mistake.

That is also why this verb, alone among the wiki's, asks. The reset destroys hand-written
prose — the notes the user typed themselves, in the notes tree, indistinguishable to
tapedeck from what an agent wrote — and a verb that can do that on a typo is a verb the
user has to be careful around. **Consent is the specification**, in SPEC-cli-008's mold:
without `--yes` the command executes nothing at all. It prints on stdout the resolved wiki
path, so a surprising `$TAPEDECK_HOME` is visible before anything is agreed to, then what
the reset would remove, then the ids it would refile in `sync`'s order, and exits 0. With
`--yes` the user has consented to exactly what that preview described. Nothing outside
`wiki/` is touched either way: the library, the archive pages and the index are untouched,
so the worst outcome of a rebuild is a wiki the user liked less, held in a repository that
still contains the one they liked.

A missing wiki exits 2, naming the path it looked for, since which wiki was resolved is the
whole question a surprising `$TAPEDECK_HOME` raises. `file` and `sync` scaffold a wiki
because filing into one is what they are for; `rebuild` is a verb about an existing wiki's
contents, and asking it to
rebuild what was never built is a usage error rather than an invitation. The preview reads
no maintainer seam — the question "what would this remove and refile" is answerable on a
machine with no agent configured — while `--yes` without a resolvable `[wiki].maintainer_command`
exits 2 naming the key, before anything is deleted, since a reset whose refill cannot run
is the one outcome nobody wants.

With `--yes` the run begins the way every wiki operation begins: whatever is pending in the
working tree is committed as `user edits` (SPEC-wiki-002), so the hand-edits sitting
uncommitted at the moment of the rebuild are in the history on the far side of the reset
rather than lost to it. Then **one reset commit**, named `wiki rebuild: reset`, which
deletes everything under `sources/` and `notes/`, rewrites `index.md` to the empty catalog
the scaffold begins from (SPEC-wiki-001), and appends a single log entry of the layout
contract's shape, `## [YYYY-MM-DD] rebuild | <subject>`. One commit rather than several,
because the state being recorded is "the old wiki, entire" and the user restoring it should
have exactly one thing to name. The `sources/` and `notes/` directories themselves remain
in the working tree, empty, as the scaffold made them — git's indifference to empty
directories is not a license to leave the wiki missing its shape.

Two files survive the reset untouched, and both survivals are the point. `CLAUDE.md` is the
user's brief and is never written by tapedeck after the scaffold (SPEC-wiki-001) — a
rebuild is most often performed *because* the brief changed, and a reset that reverted it
would erase the reason it was asked for. `log.md` keeps every entry it had: the log is
append-only mechanically (SPEC-wiki-001 and the layout contract), and a chronology that a
rebuild could clear would be a chronology that forgets its own most consequential event.
The reset is an entry in the record, not a gap in it.

The refill is `sync`, not a new sweep. Every eligible video — well-formed id, media present,
archive page rendered, by ingest's rule and the sweep's discipline of SPEC-wiki-003 — is
filed through the standard `file` operation in `upload_date`-ascending order with ties
broken by id, each with its own maintainer run, its own whole-wiki gate, and its own commit.
Because the reset left no source pages behind, every eligible video is unfiled and every one
of them is refiled; that is the only difference between this verb and `sync`, and it is
entirely contained in the reset. Per-video failure is tolerated exactly as `sync` tolerates
it — reported on stderr, rolled back on its own, the sweep continuing — and the run ends
with the same one-line summary and the same exit semantics: 0 when nothing failed, 1
otherwise. A rebuild in which three maintainer runs failed is not a corrupt wiki; it is a
wiki three videos short, and the next `sync` finishes it.
